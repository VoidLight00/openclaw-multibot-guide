병렬 실행 원리

하나의 Gateway 프로세스가 어떻게 여러 텔레그램 봇을 동시에 처리하는지, 내부 아키텍처와 설정 방법을 깊이 알아봅니다.

Deep Dive Node.js Event Loop Long Polling

[ENGINE] 핵심 원리: 단일 프로세스, 다중 봇

OpenClaw는 하나의 Node.js 프로세스로 여러 텔레그램 봇을 동시에 운영합니다. 별도의 프로세스나 스레드를 생성하지 않고도 가능한 이유는 Node.js의 비동기 이벤트 루프 덕분입니다.

병렬 실행 아키텍처 
┌───────────────────────────────────────────────────────┐
│              openclaw-gateway (단일 프로세스)            │
│                Node.js Event Loop                      │
│                    Port 18789                          │
│                                                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌────────┐ │
│  │ Bot #1   │  │ Bot #2   │  │ Bot #3   │  │ Bot #N │ │
│  │ Token A  │  │ Token B  │  │ Token C  │  │ Token N│ │
│  │Long-Poll │  │Long-Poll │  │Long-Poll │  │Long-   │ │
│  │          │  │          │  │          │  │Poll    │ │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └───┬────┘ │
│       │             │             │             │      │
│       ▼             ▼             ▼             ▼      │
│  ┌─────────────────────────────────────────────────┐   │
│  │            bindings 라우팅 테이블                  │   │
│  └─────────────────────────────────────────────────┘   │
│       │             │             │             │      │
│       ▼             ▼             ▼             ▼      │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌────────┐ │
│  │ Agent A  │  │ Agent B  │  │ Agent C  │  │Agent N │ │
│  │ Claude   │  │ Gemini   │  │  GPT     │  │ Any    │ │
│  └──────────┘  └──────────┘  └──────────┘  └────────┘ │
└───────────────────────────────────────────────────────┘

왜 하나의 프로세스로 충분한가?

[ASYNC] 비동기 I/O

텔레그램 Long Polling은 네트워크 I/O입니다. Node.js는 I/O 대기 중 다른 작업을 처리할 수 있어 CPU를 낭비하지 않습니다.

[LOOP] 이벤트 루프

각 봇의 폴링 요청이 이벤트 큐에 등록됩니다. 메시지가 도착하면 콜백이 실행되어 해당 에이전트로 전달됩니다.

[TOKEN] 독립적 연결

각 봇 토큰은 텔레그램 Bot API와 별도의 HTTP 연결을 유지합니다. 하나의 봇이 바쁘더라도 다른 봇에 영향을 주지 않습니다.

[MEM] 낮은 리소스

프로세스 하나로 동작하므로 메모리 사용량이 적습니다. 봇 4개를 운영해도 약 50~80MB 수준입니다.

[i] Long Polling vs Webhook

OpenClaw은 기본적으로 Long Polling 방식을 사용합니다. Gateway가 텔레그램 서버에 "새 메시지 있어?" 하고 계속 물어보는 방식입니다. 별도의 공인 IP나 SSL 인증서가 필요 없어 로컬 환경(Mac Mini, NAS 등)에 적합합니다.

[ROUTE] 메시지 라우팅 상세

여러 봇이 동시에 메시지를 수신할 때, Gateway는 bindings 설정을 기반으로 각 메시지를 올바른 에이전트에게 전달합니다.

라우팅 흐름

메시지 라우팅 과정 
사용자 A → @MyBot1 에 메시지 전송
사용자 B → @MyBot2 에 메시지 전송     (동시에 발생 가능)
사용자 C → @MyBot3 에 메시지 전송

        ┌────────────────────────────────────┐
        │           Gateway 수신              │
        │  Bot1 Token → accountId: "bot1"    │
        │  Bot2 Token → accountId: "bot2"    │
        │  Bot3 Token → accountId: "bot3"    │
        └─────────────┬──────────────────────┘
                      │
                      ▼
        ┌────────────────────────────────────┐
        │       bindings 매칭 엔진            │
        │                                    │
        │  for each binding:                 │
        │    if msg.channel == match.channel  │
        │    && msg.accountId == match.accountId │
        │    → route to binding.agentId      │
        └─────────────┬──────────────────────┘
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
     Agent "alpha"  Agent "beta"  Agent "gamma"
     (Claude Opus)  (Gemini Pro)  (GPT-4)

Binding 구조 이해

각 binding은 match 조건과 목적지 agentId로 구성됩니다.

binding 예시 
{
  "bindings": [
    {
      "agentId": "alpha",           // → 이 에이전트로 전달
      "match": {
        "channel": "telegram",      // 텔레그램 채널에서 온 메시지 중
        "accountId": "bot1"         // "bot1" 계정으로 들어온 것만
      }
    },
    {
      "agentId": "beta",
      "match": {
        "channel": "telegram",
        "accountId": "bot2"
      }
    }
  ]
}
필드 역할 매칭 대상
agentId 메시지를 처리할 에이전트 agents.list[].id 와 일치
match.channel 메시징 채널 종류 "telegram", "discord" 등
match.accountId 채널 내 계정 식별자 channels.telegram.accounts 의 키
[!] 매칭 규칙

accountId는 channels.telegram.accounts에 정의한 키 이름과 정확히 일치해야 합니다. 대소문자를 구분하므로 주의하세요.

[GEAR] 동시 처리 설정

봇이 동시에 여러 메시지를 받을 수 있습니다. maxConcurrent 설정으로 에이전트당 동시 처리 수를 제어합니다.

동시 처리 설정 
{
  "agents": {
    "defaults": {
      "maxConcurrent": 4,
      "subagents": {
        "maxConcurrent": 8
      }
    }
  }
}
설정 기본값 설명
maxConcurrent 4 에이전트 하나가 동시에 처리할 수 있는 대화 수
subagents.maxConcurrent 8 에이전트의 도구 호출(MCP, Skills) 동시 실행 수

설정 가이드라인

[LOW] 저사양 환경

Mac Mini (8GB RAM) 또는 NAS

권장 설정 
"maxConcurrent": 2,
"subagents": { "maxConcurrent": 4 }

[MID] 일반 환경

Mac Mini (16GB+) 또는 일반 서버

권장 설정 
"maxConcurrent": 4,
"subagents": { "maxConcurrent": 8 }
[i] 비용 주의

maxConcurrent를 높이면 동시에 여러 AI API 호출이 발생합니다. API 비용과 쿼터 제한을 고려하여 적절히 설정하세요. 특히 Claude Opus 같은 고비용 모델은 낮게 설정하는 것을 권장합니다.

[AUTO] 자동 시작 설정 (macOS)

Mac Mini를 서버로 사용하는 경우, LaunchAgents를 설정하면 재부팅 시 Gateway가 자동으로 시작됩니다.

plist 파일 생성

아래 내용으로 LaunchAgent를 생성합니다.

~/Library/LaunchAgents/ai.openclaw.gateway.plist 
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>ai.openclaw.gateway</string>

  <key>ProgramArguments</key>
  <array>
    <string>/usr/local/bin/openclaw</string>
    <string>gateway</string>
    <string>start</string>
  </array>

  <key>RunAtLoad</key>
  <true/>

  <key>KeepAlive</key>
  <true/>

  <key>StandardOutPath</key>
  <string>/Users/YOUR_USERNAME/.openclaw/logs/gateway.log</string>

  <key>StandardErrorPath</key>
  <string>/Users/YOUR_USERNAME/.openclaw/logs/gateway.err.log</string>

  <key>EnvironmentVariables</key>
  <dict>
    <key>PATH</key>
    <string>/usr/local/bin:/usr/bin:/bin</string>
  </dict>
</dict>
</plist>

경로 확인

ProgramArguments의 openclaw 경로를 확인합니다.

Terminal 
# openclaw 실행 파일 경로 확인
which openclaw

# npm global 설치 경로 확인
npm config get prefix

출력된 경로를 plist의 ProgramArguments에 반영하세요.

서비스 등록 및 시작

Terminal 
# 로그 디렉토리 생성
mkdir -p ~/.openclaw/logs

# 서비스 등록
launchctl load ~/Library/LaunchAgents/ai.openclaw.gateway.plist

# 서비스 시작
launchctl start ai.openclaw.gateway

동작 확인

Terminal 
# 서비스 상태 확인
launchctl list | grep openclaw

# 프로세스 확인
ps aux | grep openclaw

# 로그 확인
tail -f ~/.openclaw/logs/gateway.log
plist 키 값 설명
RunAtLoad true 로그인 시 자동 시작
KeepAlive true 크래시 시 자동 재시작
StandardOutPath 로그 경로 표준 출력 로그 파일
StandardErrorPath 에러 로그 경로 에러 출력 로그 파일

[AUTO] 자동 시작 설정 (Linux / WSL2)

Linux 서버나 WSL2 환경에서는 systemd를 사용합니다.

서비스 파일 생성

/etc/systemd/system/openclaw-gateway.service 
[Unit]
Description=OpenClaw Gateway
After=network.target

[Service]
Type=simple
User=YOUR_USERNAME
ExecStart=/usr/local/bin/openclaw gateway start
Restart=always
RestartSec=10
Environment=PATH=/usr/local/bin:/usr/bin:/bin
Environment=HOME=/home/YOUR_USERNAME

[Install]
WantedBy=multi-user.target

서비스 등록 및 시작

Terminal 
# 서비스 등록
sudo systemctl daemon-reload
sudo systemctl enable openclaw-gateway

# 서비스 시작
sudo systemctl start openclaw-gateway

# 상태 확인
sudo systemctl status openclaw-gateway

[PLUS] 기존 멀티봇에 새 봇 추가하기

이미 운영 중인 멀티봇 환경에 새로운 봇을 추가하는 방법입니다.

텔레그램 봇 생성

텔레그램에서 @BotFather에게 /newbot 명령을 보내 새 봇을 생성하고, 봇 토큰을 받습니다.

Workspace 생성

새 에이전트의 작업 디렉토리를 만듭니다.

Terminal 
# 새 에이전트 디렉토리 생성
mkdir -p ~/my-new-agent

# 필수 파일 생성
cat > ~/my-new-agent/AGENTS.md << 'EOF'
# AGENTS.md
이 에이전트의 워크스페이스입니다.
EOF

cat > ~/my-new-agent/SOUL.md << 'EOF'
# 성격 정의
당신은 [역할]입니다. [성격 설명]
EOF

Config에 추가

~/.openclaw/openclaw.json에 3곳을 수정합니다.

1. agents.list 에 추가 
{
  "agents": {
    "list": [
      // ... 기존 에이전트들 ...
      {
        "id": "newagent",
        "workspace": "/home/username/my-new-agent",
        "model": {
          "primary": "google/gemini-2.0-flash"
        }
      }
    ]
  }
}
2. channels.telegram.accounts 에 추가 
{
  "channels": {
    "telegram": {
      "accounts": {
        // ... 기존 계정들 ...
        "newbot": {
          "botToken": "YOUR_NEW_BOT_TOKEN"
        }
      }
    }
  }
}
3. bindings 에 추가 
{
  "bindings": [
    // ... 기존 바인딩들 ...
    {
      "agentId": "newagent",
      "match": {
        "channel": "telegram",
        "accountId": "newbot"
      }
    }
  ]
}

Gateway 재시작

Terminal 
# Gateway 재시작
openclaw gateway restart

# 새 봇이 응답하는지 테스트
# → 텔레그램에서 새 봇에게 메시지를 보내보세요
[!] 추가 시 체크리스트

☐ agents.list[].id 가 고유한가?
☐ accounts 키와 bindings.match.accountId 가 일치하는가?
☐ bindings.agentId 가 agents.list[].id 와 일치하는가?
☐ 봇 토큰이 다른 기기에서 사용 중이지 않은가?
☐ workspace 디렉토리가 실제로 존재하는가?

[CHECK] 상태 확인 및 디버깅

멀티봇이 정상적으로 병렬 실행되고 있는지 확인하는 방법입니다.

프로세스 확인

Terminal 
# Gateway 프로세스 확인
ps aux | grep openclaw

# 포트 사용 확인 (기본 18789)
lsof -i :18789

# OpenClaw 상태 확인
openclaw status

로그 확인

Terminal 
# 실시간 로그 모니터링

# 에러 로그 확인
tail -50 ~/.openclaw/logs/gateway.err.log

# 특정 에이전트 로그 필터링
grep "agent:myagent" ~/.openclaw/logs/gateway.log

일반적인 문제

[X] 봇이 응답하지 않음

원인 해결
Gateway 미실행 openclaw gateway start
봇 토큰 오류 BotFather에서 토큰 재확인
Binding 누락 bindings 배열에 해당 봇 추가
다른 기기에서 같은 토큰 사용 중 다른 기기의 Gateway 중지

[X] 429 쿼터 에러 (Too Many Requests)

동일 AI 제공자를 여러 에이전트가 사용할 때 쿼터 제한에 걸릴 수 있습니다.

해결 방법 설명
maxConcurrent 낮추기 동시 요청 수를 줄여 쿼터 분산
Auth Order 설정 에이전트별 다른 OAuth 계정으로 쿼터 분리
모델 분산 에이전트마다 다른 AI 모델 사용

자세한 내용: 5. Config 설정 → Auth Order

[X] Gateway 시작 실패

진단 명령어 
# Config 문법 검사
cat ~/.openclaw/openclaw.json | python3 -m json.tool

# 자세한 에러 로그 확인
openclaw gateway start --verbose

# 자동 수복 시도
openclaw doctor --fix

[OK] 요약

병렬 실행의 핵심 포인트

✓ 단일 Gateway 프로세스가 Node.js 이벤트 루프로 모든 봇을 동시 관리

✓ 각 봇 토큰은 독립적인 Long Polling 연결 유지

✓ bindings가 수신 메시지를 올바른 에이전트로 라우팅

✓ maxConcurrent로 에이전트별 동시 처리 수 제어

✓ LaunchAgents / systemd로 자동 시작 및 재시작 설정 가능

✓ 새 봇 추가는 config 3곳만 수정하면 완료
